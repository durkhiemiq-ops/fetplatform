Redis is genuinely load-bearing

Not just configured — real traffic writes keys. The DRF rate limiter persists :1:throttle_anon_127.0.0.1 into the container, and attendance QR tokens are stored there with a TTL.

One environment caveat

Open the app at localhost:3000. Cookies are host-only with SameSite=Lax, so opening it via 127.0.0.1 or a LAN IP breaks authentication even though the page loads.

Security finding

The forced password change was never enforced

Documented in three places. Implemented in none of them.

What the documentation promised

  • README: "roster accounts are locked out until they replace the temporary password"
  • Business rule BR-003: a user must never gain permissions by modifying a frontend request — authorization is enforced by the backend.
  • Business rule BR-002: role and access changes require an authorised administrator.

What the code actually did

  • must_change_password was written at roster upload and cleared at password change.
  • It was read by one serializer and never checked anywhere else — no permission class, no middleware, no view guard.
  • The only protection was a client-side redirect in React, which any user can skip by navigating directly.

Why it mattered

A student provisioned from a departmental roster signs in with a temporary password. Before this fix, that account could read announcements, browse projects and pull its own attendance while the password was still known to whoever handed it over. The lockout was cosmetic.

Remediation

Enforcement moved to the only place that cannot be bypassed

The design decision that mattered.

Rejected: a permission class

Adding a check to DEFAULT_PERMISSION_CLASSES looks right and does almost nothing — over 100 views declare their own permission_classes, which silently override the default. The check would be skipped nearly everywhere.

Adopted: the authentication layer

Every authenticated request passes through the JWT authenticator. The rule lives there, so no view can opt out of it, and a student cannot escape it by swapping to a Bearer header.

Proved live against a real account holding a temporary password: /auth/me/ → 200, /dashboard/, /projects/, /announcements/, /students/me/courses/, /notifications/ → 403 each.

Remediation

Two smaller defects, same review

Contradictory validation message

Level validation accepted 200/300/400/500 but its error message advertised L200, L300… So a user who followed the instructions exactly was rejected for doing so. The bug existed in two serializers.

Fixed one shared VALID_LEVELS constant now drives both the check and the message, so they cannot drift apart again.

Dead authorisation constant

STUDENT_REGISTRATION_DOMAINS declared the rule that students register on a @ubuea.cm address — and was referenced nowhere. The rule it documented was never enforced.

Left as-is, deliberately Wiring it in would contradict a passing test that explicitly allows lecturer self-registration with any address. That is a product decision, not a bug fix — see the gaps slide.

Regression safety

All 326 pre-existing tests still pass after the changes. We added 23 new tests across two files and finished at 349 passing, 0 failing.

New capability

Security & Audit Console

Filling a gap the specifications explicitly name.

The gap

Audit records were already being written from across the platform — sign-ins, sign-outs, account creation, announcement pins, role changes. Nothing could read them back.

The API specification declares three administrator roles and contains zero admin endpoints. The role matrix nevertheless grants "Access audit logs" to System Administrators.

What we shipped

  • GET /api/v1/audit/logs/ — paginated, filterable trail
  • GET /api/v1/audit/summary/ — 24h headline numbers
  • An admin console page, reachable at /admin/audit
  • 15 tests covering access control, read-only guarantees and filters

Admin only

A student requesting the log gets 403. Verified live, and pinned by tests.

Read-only by construction

No mutation endpoints exist. DELETE returns 405. The absence is the control, per BR-211.

Filters can't become an attack

Filters are whitelisted, not passed through. A SQL-injection string in any parameter is ignored rather than executed.

Recommendation

What we would do next

1 · Close the registration hole

Owner: accounts. New lecturer registrations require administrator approval. Until then, consider disabling lecturer self-registration in configuration. This is the highest-value fix remaining.

2 · Provision PostgreSQL

Owner: platform. Stand up the container, migrate, and prove the app on the production-shaped database. Removes the SQLite-only limitation and unblocks the compose deployment.

3 · Close the UI gap

Owner: frontend. Materials, classes and assessment marks already have tested APIs. Screens here cost the least and show the most.

Make it permanent

Pin rule IDs to test names. The moment a requirement has a number, it can be regression-tested forever, and coverage becomes a number on a dashboard instead of an opinion in a meeting.

Close the documentation drift

The README documents 27 endpoints that no longer exist and describes Docker as "coming soon" while the compose file sits in the repository. Generate the endpoint table from the resolver so it cannot go stale.
